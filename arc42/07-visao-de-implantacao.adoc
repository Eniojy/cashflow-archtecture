== Distribuição e isolamento

As APIs e o Worker são implantados separadamente para permitir escala, limites e rollback
independentes. Os processos são stateless; o estado durável permanece nos bancos e no Pub/Sub.
Cada workload utiliza uma identidade de serviço com permissões mínimas.

O PostgreSQL de Lançamentos é configurado para alta disponibilidade entre zonas. Essa configuração
protege falhas de instância e zona, mas não substitui uma estratégia para desastre regional.
MongoDB Atlas utiliza réplica, confirmação por maioria e backup contínuo de acordo com o plano
contratado.

== Escalabilidade

* Lançamentos API escala por concorrência HTTP, respeitando o limite de conexões do PostgreSQL.
* Consolidado API escala por consultas, respeitando o pool do MongoDB.
* Consolidado Worker escala por backlog, com teto de concorrência para proteger o banco.
* Outbox Publisher processa lotes pequenos; aumentar instâncias exige reivindicação segura por
  lease.
* Instâncias mínimas podem ser configuradas quando a latência de inicialização comprometer a meta.

== Entrega e rollback

Cada imagem deve ser imutável, identificável e promovida entre ambientes. O rollout deve ser
gradual e acompanhado por taxa de erro, latência e sinais de integridade. Se uma nova revisão
degradar o serviço, o tráfego volta à revisão estável. Mudanças de banco precisam ser compatíveis
com a versão anterior durante o período de transição.

== Recuperação

* Falha do Consolidado não interrompe Lançamentos; eventos aguardam na Outbox ou no Pub/Sub.
* Falha do Pub/Sub mantém a intenção de publicação na Outbox.
* Falha do PostgreSQL impede novas confirmações até o failover ou restauração.
* Falha do MongoDB atrasa a projeção; mensagens permanecem retidas até o retorno.
* Após a recuperação, o backlog é drenado gradualmente e uma reconciliação confirma a convergência.
